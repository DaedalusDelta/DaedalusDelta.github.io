## Main finding

Yes: TU Delft Fabrics supports energy-based speed regulation and programmable damping. These can change speed along its geometric behavior, but do not guarantee faithful tracking of an arbitrarily moving attractor. For the present bend/undertracking problem, a curvature-aware reference clock with continuous pose coordination is the most direct first change; damping is an additional tuning variable. Dynamic attractors are the library's more principled moving-reference interface. Their integration is a separate change requiring validation.

The reviewed [controller snapshot](study-artifacts/execution-speed-v2/controller_snapshot/fabric_control.py) defines three `staticSubGoal`s and supplies new goal positions/orientation-axis vectors each call. It does not supply target velocities or accelerations. It evaluates the fabric on its integrated command state `self.q,self.v`, clips acceleration and velocity, clips joint position, then clips command position to measured position ±0.10 rad without reconciling velocity. Thus target undertracking can arise from moving-reference lag, command/measurement separation, saturation, competing orientation/avoidance terms, and simulator actuation. Increasing attractor stiffness alone cannot identify which dominates.

## Exact installed interfaces and equations

The authoritative local sources are [planner](study-artifacts/.venv/lib/python3.10/site-packages/fabrics/planner/parameterized_planner.py:236), [configuration](study-artifacts/.venv/lib/python3.10/site-packages/fabrics/planner/configuration_classes.py:9), [Damper](study-artifacts/.venv/lib/python3.10/site-packages/fabrics/diffGeometry/speedControl.py:9), and [execution energy](study-artifacts/.venv/lib/python3.10/site-packages/fabrics/components/energies/execution_energies.py:4). Upstream counterpart: [v0.10.0 planner](https://github.com/tud-amr/fabrics/blob/v0.10.0/fabrics/planner/parameterized_planner.py).

* Default `forcing_type='speed-controlled'`. For static goals, the implemented acceleration is `a = a_forced - (A + beta) qdot`, where `A = eta*alpha_execution + (1-eta)*alpha_forced_execution`. The source passes **negative** `A` and **negative** `alpha_geometry` into `Damper.substitute_beta`. The current expression `b + max(0,a_ex-a_le)` therefore gives total velocity coefficient `b + max(A,alpha_geometry)`. Preserve that sign convention when changing damping.
* Current `b=8*rate`; potential is `200*rate**2 * dot(x,x)`. Here `rate` changes stiffness, damping, acceleration clipping, and velocity clipping together. It is not an independent speed command. `base_energy=0.5*0.05*dot(qdot,qdot)` changes the base geometry metric; it is not a desired speed setpoint.
* `set_components(goal=...)` installs default execution energy `L_ex=dot(qdot,qdot)` and calls `set_speed_control()`. Default `damper_eta` is a fixed sigmoid of squared joint speed. Neither configuration exposes a simple `desired_speed` scalar.
* To make damping adjustable per call, configure `damper_beta="sym('beta') + ca.fmax(0, sym('a_ex') - sym('a_le'))"`. The runtime input is `beta_damper`, because [the parser](study-artifacts/.venv/lib/python3.10/site-packages/fabrics/helpers/functions.py:43) appends the leaf/damper suffix. Keep it positive and smooth. `beta` expressions get attractor error `x`, but **do not get `xdot`**; supply an externally computed speed-dependent scalar through a symbol if needed.
* `damper_eta` accepts `sym('ex_lag')`, which is substituted with the actual execution Lagrangian. An explicitly proposed speed transition is `0.5*(1+ca.tanh(sym('k')*(sym('E_target')-sym('ex_lag'))))`, with runtime `k_damper,E_target_damper`. This blends two energization coefficients; it is **not** an exact energy tracking law. With default energy, `E_target` has units of squared joint speed, not TCP speed. Extra positive damping changes the achieved equilibrium.
* To replace the energy, create `Lagrangian(expression, var=planner.variables)`, then call `planner.set_execution_energy(L)`, `planner.set_speed_control()`, and `planner.concretize(mode='acc')` **after** `set_components`. Replacing it before `set_components` is overwritten. A candidate TCP-sensitive energy is `0.5*dot(J_tcp*qdot,J_tcp*qdot) + 0.5*epsilon*dot(qdot,qdot)` with `epsilon>0` so the seven-joint metric is not rank deficient. This measures TCP motion plus regularized nullspace motion; it is not pure TCP speed. For position-dependent custom energies, use `ex_lag` in eta: its parser constructs `xdot` from *all* symbolic variables of the energy, so default `dot(xdot,xdot)` can include positions as well as velocities.

Changing the conserved energy defines what speed means; it does not independently prescribe an arbitrary speed history. Multiplying a constant quadratic energy by a scalar mostly cancels out in its energization coefficient (apart from numerical regularization), so merely scaling `L_ex` is not a robust speed knob.

## Geometry preservation and moving references

For an unforced HD2 geometry, velocity-aligned acceleration changes traversal timing without changing the path; HD2 means `h(q,c*qdot)=c**2*h(q,qdot)`. The research speed-control construction additionally constrains energization/damping to retain convergence under potential forcing. This is not a theorem that a forced robot will trace exactly the same curve under arbitrary damping changes or time-varying targets. See the authors' [Geometric Fabrics paper, Sections III and V–VI](https://mandyxie.github.io/geometric_fabrics_rss.pdf). In particular, a position-only attracting force does not scale quadratically with velocity, and this controller changes that force over time.

The installed [dynamic attractor](study-artifacts/.venv/lib/python3.10/site-packages/fabrics/components/leaves/dynamic_attractor.py:11) and [dynamic leaf](study-artifacts/.venv/lib/python3.10/site-packages/fabrics/components/leaves/dynamic_leaf.py:6) support relative position/velocity and target acceleration. `set_goal_component` selects this path for `analyticSubGoal` or `splineSubGoal`; it does **not** test for `dynamicSubGoal`. Goal 0 inputs are `x_ref_goal_0_leaf`, `xdot_ref_goal_0_leaf`, and `xddot_ref_goal_0_leaf`, plus `weight_goal_0`. The library dynamically pulls these terms back and uses a reference-dependent velocity correction. Theory and experiments are in TU Delft's [Dynamic Optimization Fabrics, Sections IV–VI](https://tud-hummus.github.io/assets/dynamic_fabrics.pdf). This is the appropriate library feature to investigate for feedforward tracking, but its assumptions must be checked for the current orientation-axis goals and discontinuous phase switches.

## Practical sequence for this controller

1. Keep a geometric path `p(s)` and schedule progress continuously. With arc-length parameter `s`, compute curvature `kappa=||p' cross p''||/||p'||**3` and propose `v_curve=sqrt(a_normal_max/max(kappa,kappa_floor))`. Set desired speed from the minimum of cruise, curvature, orientation-rate, and proximity/contact limits. Smooth speed and bound tangential acceleration; start slowing before the bend using lookahead. For non-arc-length paths use `s_dot=v/||p'||`. These are elementary kinematic design formulas, not built-in Fabrics APIs.
2. Slow the reference clock continuously when measured tracking error grows; avoid replacing the old orientation gate with another hard stop. Account for both orientation and position in progress regulation. If using dynamic references, derive consistent `p_dot=p_s*s_dot` and `p_ddot=p_ss*s_dot**2+p_s*s_ddot` from the same clock. A temporal reparameterization preserves the **reference** path, while actual robot path fidelity remains measured.
3. Diagnose undertracking by recording reference/measured TCP speed, along-path and cross-path error, orientation error, command/measured joint gap, acceleration/velocity clipping fractions, and speed versus curvature. Larger damping may reduce overshoot but worsen moving-target lag. In a scalar unsaturated approximation `x_ddot=K(g-x)-B*x_dot`, constant-speed target lag is `B*v_target/K`; this is explanatory, not an exact model of the composed robot fabric.
4. Accept against physical endpoint completion, floor/self/object clearances, no pauses away from contact, and desired bend/cruise speed contrast. The current model has no external obstacles (`number_obstacles=0`), only selected link spheres, one plane, and two self-collision pairs. Its finite-step integration, per-coordinate clipping, surrogate-state evaluation, and incomplete geometry prevent treating paper guarantees as a collision certificate for this execution.

No conclusion here establishes a safe or natural trajectory. The next verifiable outcome is a measured comparison from the parent implementation showing curvature-dependent speed, reduced actual target lag, and preserved physical completion/clearance.
